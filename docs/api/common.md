# API 공통 규칙

노션 "📘 API 공통 규칙 (1)" 페이지(간지톤 / 자료모음)를 기준으로 정리했다. 원문에서 **확정**과 **제안**을 구분해 표시했다. 제안은 구현 전에 바뀔 수 있다. 개별 API 페이지에 반복된 프론트용 메모도 마지막에 같이 모았다.

## 1. 확정 사항

| 항목 | 내용 |
| --- | --- |
| 서비스 형태 | 웹앱 |
| 인증 | Access Token + Refresh Token |
| 인증 헤더 | `Authorization: Bearer {accessToken}` |
| Access Token | 유효시간 **1시간**, 클라이언트 **메모리에만** 저장 |
| Refresh Token | 유효시간 **14일**, HttpOnly·Secure **쿠키**, 서버에서 회전·폐기 관리 |
| Refresh 갱신 | 회전해서 새로 발급하면 그 시점부터 다시 14일 (계속 쓰면 만료가 연장됨) |
| 쿠키 SameSite | 속성은 사용, 값은 배포 도메인 확정 후 결정 |
| 성공 응답 | 본문이 있으면 `{ "data": ... }`로 감싼다. 성공 여부는 **HTTP 상태 코드**로 판단하고 `success` 필드는 없다 |
| 고민 목록 | 진입 시 한 번 무작위로 구성, 적격 고민 최대 100개를 한 번에 응답 |
| 고민 목록 스크롤 | 받은 목록 안에서만 스크롤. 추가 조회·재추첨 없음 |
| 상세에서 돌아오기 | 기존 목록·순서·스크롤 위치 유지 |

Access Token을 `localStorage`·`sessionStorage`에 저장하지 않는다. Refresh Token은 프론트 JS가 읽지 않는다(쿠키로만 오간다).

## 2. 토큰 재발급 흐름 (구현 제안)

1. 로그인 성공 시 Access Token은 응답 본문, Refresh Token은 쿠키로 받는다.
2. API 인증에는 Access Token을 쓴다.
3. Access Token 만료가 확인되면 재발급 API를 호출한다.
4. 서버가 Refresh Token의 유효기간·폐기 여부·현재 사용 가능 여부를 확인한다.
5. 성공하면 기존 Refresh Token을 무효화하고 새 Refresh Token과 Access Token을 발급한다.
6. 재발급이 실패하면 로그인 화면으로 보낸다.

프론트가 지킬 것

- 새로고침으로 메모리의 Access Token이 사라지면 **쿠키를 이용한 재발급으로 인증 상태를 복원**한다.
- 동시에 여러 API가 만료 응답을 받아도 **재발급 요청을 중복 실행하지 않는다**(하나만 실행하고 결과 공유).
- 재발급이 성공하면 실패했던 원래 요청을 **최대 한 번** 재시도한다.
- **모든 401을 재발급 대상으로 취급하지 않는다.** 만료(`AUTH_ACCESS_TOKEN_EXPIRED`)일 때만 재발급한다.
- 로그아웃은 서버 세션 폐기 + 쿠키 제거 + 메모리의 Access Token 제거.
- 토큰 원문과 비밀번호를 로그나 오류 메시지에 남기지 않는다.

미결정: Refresh Token으로 이미 발급된 Access Token이 로그아웃 후에도 최대 1시간 유효한 점을 허용할지, 로그인 유지 절대 상한을 둘지, 재사용 감지 시 세션 처리, 쿠키 Domain·Path·SameSite·CORS·CSRF 방어.

## 3. 고민 목록 규칙 (확정)

| 사용자 동작 | 목록 처리 |
| --- | --- |
| 목록에 처음 진입 | 서버가 무작위로 구성해 최대 100개 응답 |
| 스크롤을 아래로 이동 | 받은 데이터 안에서만 표시. 추가 호출·재추첨 없음 |
| 고민 상세 진입 | 현재 목록·순서·스크롤 위치를 유지할 수 있게 화면 상태 보존 |
| 상세에서 목록으로 복귀 | 기존 목록 재사용 (신규 진입으로 취급하지 않음) |
| 적격 고민이 100개 미만 | 있는 개수만 반환 |
| 적격 고민 없음 | 빈 배열 |

- 프론트는 받은 배열 순서를 유지하고, 상세 복귀를 위해 **목록과 스크롤 상태를 보존**한다. 일반적인 리렌더·화면 재표시를 신규 진입으로 보고 다시 조회하지 않는다.
- 서버는 목록 생성 뒤에도 상세 조회·답장 작성 때 삭제·접수 마감·권한을 다시 확인한다.
- 한 목록 안에서는 같은 고민이 중복되지 않는다. 서로 다른 진입 사이의 중복 노출을 막는 정책은 아니다.
- 이 목록은 `page`·`cursor`·`nextCursor`·`hasNext`를 쓰지 않는 안이다. 응답 `count`는 이번 응답에 포함된 개수일 뿐 전체 고민 수가 아니다.
- 다른 메뉴 재진입·브라우저 새로고침을 새 목록 생성으로 볼지는 아직 합의 전이다.

## 4. API 주소·메서드 (제안)

| 항목 | 기준 |
| --- | --- |
| 공통 접두사 | `/api/v1` |
| 경로 | 영어 소문자, 자원 이름은 복수 명사, 여러 단어는 하이픈 |
| 개별 대상 | Path Parameter에 자원 ID |
| 조회 조건 | Query Parameter |
| 요청 본문 | 기본 JSON (파일 업로드는 별도 규칙) |
| GET | 조회. 개봉·보상 지급 같은 동작을 일으키지 않는다 |
| POST | 생성, 또는 개봉·완료·취소 등 별도 처리 |
| PATCH | 일부 수정 |
| PUT | 자원 전체 교체가 필요한 경우 |
| DELETE | 삭제 |

목록 조회에서 현재 시각으로 숙성·휴식 상태를 **계산**해 보여주는 것과, 실제 개봉·완료 **처리**는 구분한다.

## 5. 데이터 표현 (제안)

| 항목 | 기준 |
| --- | --- |
| JSON 필드명 | `camelCase` |
| ID 필드명 | `userId`, `recordId`처럼 대상이 드러나게 |
| ID 타입 | **문자열** (DB BIGINT와 API 표현을 구분). 양의 10진수 문자열 (예: `"101"`) |
| 시각 | UTC ISO 8601 (예: `2026-11-08T03:00:00Z`) |
| 날짜 | `YYYY-MM-DD` |
| 오늘·하루 한도 | `Asia/Seoul` 기준 |
| 시간 조건 | 숙성·휴식 종료·보상 제한은 **서버 시각**으로 판단 |
| 상태·선택값 | 고정 문자열 코드. 표시 이름과 분리 |
| 빈 목록 | `[]` |
| 선택 응답 필드 | 값이 없으면 `null`. 보안상 숨길 필드는 스키마에서 제외 |
| PATCH에서 필드 누락 | 기존 값 유지 |
| PATCH에서 `null` | 값 제거를 허용한 필드만 수용, 나머지는 입력 오류 |
| 필수값·길이·범위 | API별로 명세하고 서버도 검증 |
| 요청의 `userId` | 쓰지 않는다. 인증된 사용자 정보로 본인을 식별 |
| 이메일·공백 | 가입·로그인·중복 확인에 같은 정규화 규칙 (세부 규칙은 합의 전) |

고민 외의 목록(감정 기록·보관함·양털 내역)은 화면 요구에 맞춰 페이지 또는 커서 방식을 따로 정한다. 고민 목록의 "최대 100개" 정책을 모든 목록에 적용하지 않는다.

현재 초안의 목록 파라미터는 `page`(0부터)·`size`와 응답 `page`·`size`·`hasNext`다.

| API | size 기본 / 상한 |
| --- | --- |
| 감정 기록 목록 | 20 / 100 |
| 내 치즈 목록, 치즈 보관함 목록 | 20 / 50 |
| 양털 변동 내역 | 20 / 100 |

## 6. 응답·오류 처리

### 성공 응답 (확정)

```json
{ "data": { "recordId": "123" } }
```

`204`는 본문이 없고 `data`도 없다.

### 오류 응답 (제안)

```json
{
  "code": "COMMON_INVALID_REQUEST",
  "message": "입력값을 확인해주세요.",
  "fieldErrors": [
    { "field": "memo", "reason": "허용된 글자 수를 초과했습니다." }
  ]
}
```

| 항목 | 규칙 |
| --- | --- |
| code | 도메인과 의미를 담은 영문 대문자·밑줄 (예: `EMOTION_RECORD_NOT_FOUND`) |
| message | 사용자에게 보여도 되는 한국어 문구 |
| fieldErrors | 입력 필드별 오류 목록, 없으면 `[]` |
| 프론트 분기 | **메시지 문구가 아니라 HTTP 상태와 `code`로** 분기한다 |
| 내부 오류 | 스택 트레이스·SQL·비밀값을 응답에 넣지 않는다 |

### HTTP 상태 코드 (제안)

| HTTP | 사용 기준 |
| --- | --- |
| 200 | 조회·수정·동작 처리 성공 |
| 201 | 자원 생성 성공 |
| 204 | 본문 없이 성공 |
| 400 | 요청 형식·입력값 오류 |
| 401 | 인증 정보 없음·만료·유효하지 않음 |
| 403 | 인증됐지만 권한 없음 |
| 404 | 대상 없음. 타인의 비공개 자원의 존재를 숨길 때도 사용 |
| 409 | 중복 데이터, 또는 현재 상태와 요청의 충돌 |
| 429 | 요청 횟수 제한 초과 |
| 500 | 예상하지 못한 서버 오류 |

### 공통 오류 코드 (개별 API 문서에서 반복)

| HTTP | 코드 | 의미 |
| --- | --- | --- |
| 400 | COMMON_INVALID_REQUEST | 요청 형식·타입·허용 범위 오류 |
| 400 | COMMON_EMPTY_UPDATE | PATCH에 수정 가능한 필드가 하나도 없음 |
| 401 | AUTH_ACCESS_TOKEN_INVALID | Access Token 없음·위조·유효하지 않음 |
| 401 | AUTH_ACCESS_TOKEN_EXPIRED | Access Token 만료 (이때만 재발급을 시도) |
| 409 | COMMON_IDEMPOTENCY_CONFLICT | 같은 Idempotency-Key로 다른 요청이거나 처리 중 |
| 429 | AUTH_RATE_LIMITED | 요청 제한 (로그인, 인증·재설정 메일, 닉네임 확인) |
| 500 | COMMON_INTERNAL_ERROR | 예상하지 못한 서버 오류 |

## 7. 권한·변경 처리 (제안)

| 항목 | 기준 |
| --- | --- |
| 본인 식별 | 인증된 사용자 정보로 판단. 요청 `userId`만으로 권한을 인정하지 않는다 |
| 비공개 기록 | 본인의 감정 기록·보관함만 접근 가능 |
| 신규 사용자 | 초기 설정·약관을 마치지 않은 사용자가 쓸 수 있는 기능은 별도 정의 |
| 일반 가입·구글 로그인 | 이메일이 같다는 이유로 자동 연결하지 않음 |
| 중복 요청 | 양털 중복 지급·중복 차감을 막는다 |
| 트랜잭션 | 돌봄 완료·보상 거래 기록·잔액 변경처럼 함께 성공해야 하는 것은 함께 처리 |
| 반복 동작 | 재시도를 기존 성공으로 볼지 충돌로 볼지는 API별로 명시 (예: 보관·개봉은 기존 성공 200) |
| 삭제·보관·취소 | 서로 다른 의미로 정의 |
| 보상 변경 | 완료 당시 지급량을 보존. 보상 변경으로 과거 지급량을 덮어쓰지 않음 |

## 8. Idempotency-Key (개별 API 제안)

공통 규칙 원문에는 없고, 아래 4개 API 페이지에 "제안"으로 적혀 있다: **고민 작성, 돌봄 행동 완료, 돌봄 행동 완료 취소, 휴식 시작**. 중복 실행되면 안 되는 쓰기 요청에 `Idempotency-Key: {UUID}` 헤더를 붙인다.

- 같은 동작의 재시도는 같은 키, 새 동작은 새 UUID. 네트워크 오류 재시도에는 직전 키를 그대로 쓴다.
- 같은 키·같은 요청이면 최초 성공 응답을 그대로 준다. 같은 키로 다른 요청이거나 처리 중이면 `409 COMMON_IDEMPOTENCY_CONFLICT`.
- 키 범위는 (사용자, 키), 보관 24시간(제안). 재시도 응답은 최초 성공 시점의 스냅샷이므로 이후 잔액·내역은 다시 조회한다.
- 현재 ERD에 멱등 키 저장소가 없어 백엔드와 적용 여부를 합의해야 한다.

## 9. 프론트 처리 메모 (개별 API 페이지 공통 문구)

- 인증이 필요 없는 API는 회원가입·로그인·구글 로그인·이메일 인증·비밀번호 재설정이다(`auth.md`). 재발급·로그아웃은 Access Token이 아니라 Refresh Token **쿠키**를 쓴다. 그 외 모든 API는 로그인 사용자 전용이다.
- 개인 데이터 응답에는 `Cache-Control: no-store`가 붙는다(제안). PWA 서비스 워커가 `/api` 요청을 캐시하지 않도록 해야 한다.
- 개인 메모와 토큰 원문은 로그에 남기지 않는다.
- 버튼 연타 방지, 입력 길이·선택 여부 검증, 확인창, 애니메이션은 클라이언트가 처리한다. 서버도 같은 검증을 하므로 클라이언트 상태를 권한·보상·완료 판정의 근거로 삼지 않는다.
- 타인 리소스와 존재하지 않는 리소스는 같은 404로 응답한다(제안).
- 초기 설정·필수 약관을 마치지 않은 사용자가 각 API를 어디까지 쓸 수 있는지는 회원 담당자와 합의 전이다.

## 10. 남은 결정 사항 (원문)

| 항목 | 결정할 내용 |
| --- | --- |
| 배포 주소 | 프론트·백엔드 도메인 구성 |
| 쿠키·CORS | SameSite 값, 쿠키 Domain·Path, 허용 Origin·자격 증명 |
| 쿠키 인증 요청 보호 | 재발급·로그아웃의 CSRF 방어 방법 |
| Refresh Token 서버 관리 | 저장소·해시·세션별 폐기·회전 정보 구조 (ERD 반영 필요) |
| Refresh Token 재사용 | 폐기된 토큰 재사용 시 세션 처리 |
| 로그아웃 | 현재 기기만/전체 기기, Access Token 즉시 차단 여부 |
| 로그인 유지 상한 | 회전 14일 갱신 외에 절대 만료를 둘지 |
| 고민 목록 신규 진입 | 다른 메뉴 재진입·새로고침·뒤로가기에서 목록을 다시 구성할 범위 |
| 고민 후보 조건 | 본인 글·접수 마감·삭제·지역·기존 답장 여부 |
| 목록 카드 | 미리보기 길이와 반환 필드 |
| 기타 목록 | 감정 기록·보관함·양털 내역의 조회 방식과 정렬 |
| 프로젝트별 입력 정책 | 감정·행동 코드, 메모 길이, 행동 완료 횟수 |
| 파일 업로드 | 프로필 이미지 업로드 방식·형식·크기 제한 |
